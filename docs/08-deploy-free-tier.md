# StockWise — 08. Free-tier deployment (demo and first pilot)

Audience: the two developers. Cost: 0. Good for demos and a first test with one shop. When a business relies on it every day, move to the VPS plan in [01 §15](01-architecture.md#15-environments-and-deployment).

```
Browser ──► https://<site>.netlify.app ──┬─ /*      → React build (Netlify)
                                         └─ /api/*  → proxied to https://stockwise-api.onrender.com (Render, free)
                                                         │
                                                         ▼
                                                   Neon Postgres (free)
UptimeRobot / cron-job.org ──every 10 min──► /api/v1/health/live (keeps Render awake, never touches the DB)
```

| Piece | Service | Config in repo | Free-tier catch |
|---|---|---|---|
| Web + `/api` proxy | Netlify | `netlify.toml` | Proxied requests time out after ~30 s, so a sleeping API returns an error instead of waiting |
| API | Render web service | `render.yaml` | Sleeps after 15 min idle (wakes in ~1 min); 750 h/month, enough for one service 24/7 |
| Database | Neon | `neon.ts` | 0.5–1 GB storage, 100 compute-hours/month; over that, compute is suspended until next month (data kept) |

**Why the proxy matters:** the refresh cookie is `SameSite=Strict` and the web app calls the relative path `/api/v1`. Browser, pages and API must share one origin, or users are logged out every 15 minutes. Don't point the web app straight at the `onrender.com` URL.

## 1. Before you start

- Push the code and merge it into `main` (Render and Netlify deploy `main`).
- Create free accounts: [Neon](https://console.neon.tech), [Render](https://render.com), [Netlify](https://app.netlify.com), and [UptimeRobot](https://uptimerobot.com) or [cron-job.org](https://cron-job.org). Sign in to Render and Netlify with GitHub.

## 2. Database (Neon)

1. The current project is in **AWS US East (Ohio) `us-east-2`**, so `render.yaml` uses Render's `ohio` region. The API must run in the same region as the database, or every query pays a round trip across the ocean. For a new project, Frankfurt (`eu-central-1` on Neon, `frankfurt` on Render) is closer to Burundi; a Neon project's region can't be changed later, so moving means a new project plus a dump and restore (§9).
2. From **Connect**, copy both connection strings: the **pooled** one (host contains `-pooler`) and the **direct** one. Keep `?sslmode=require`.
3. From your laptop, apply migrations and seed roles and permissions (no demo shop):

   ```bash
   cd apps/api
   DATABASE_URL="<direct URL>" pnpm exec prisma migrate deploy
   DATABASE_URL="<direct URL>" SEED_DEMO=false pnpm exec prisma db seed
   ```

   Render also runs `migrate deploy` on every start, but the seed runs only from here. Without it, registration fails because there are no roles.

## 3. API (Render)

1. Render dashboard → **New → Blueprint** → pick the repo. Render reads `render.yaml` and asks for the secret values:
   - `DATABASE_URL`: Neon **pooled** URL
   - `DATABASE_URL_UNPOOLED`: Neon **direct** URL (only used for migrations)
   - `WEB_ORIGINS` and `WEB_URL`: leave a placeholder such as `https://example.com` for now; you get the real value in step 4
   - `JWT_ACCESS_SECRET` is generated by Render. Don't reuse a development secret.
2. Wait for the first deploy, then open `https://stockwise-api.onrender.com/api/v1/health`. Expect `{"status":"ok","db":"up"}`.
3. If Render gave the service a different URL (the name was taken), update the `to =` line in `netlify.toml` and push.

## 4. Web (Netlify)

1. Netlify → **Add new site → Import an existing project** → pick the repo. Build settings come from `netlify.toml`; don't override them.
2. After the deploy, note the site URL (for example `https://stockwise-bi.netlify.app`). You can rename the site under **Site configuration**.
3. Back in Render → the service → **Environment**: set `WEB_ORIGINS` and `WEB_URL` to that exact URL (`https://`, no trailing slash). Save; Render redeploys.
4. Check `https://<site>.netlify.app/api/v1/health` through the proxy.

## 5. Check the client IP the API sees (rate limits)

Login is limited per IP + email, and every route per IP. If the API trusts too few proxies, all users share Netlify's IP and hit the limit together; too many, and a client can fake its IP.

1. In Render, set `SHOW_CLIENT_IP=true` and wait for the redeploy.
2. Open `https://<site>.netlify.app/api/v1/health/live`. It returns `ip` and the full `ips` chain.
3. Compare `ip` with your real public IP (search "what is my IP"):
   - It matches: `TRUST_PROXY` is right.
   - It's a Netlify or Render address, and your IP is further left in `ips`: increase `TRUST_PROXY` by one and check again.
   - `ips` has an address left of yours that you didn't send: decrease `TRUST_PROXY`.
4. Set `SHOW_CLIENT_IP=false` again.

## 6. Keep the API awake

Create a monitor in UptimeRobot or cron-job.org:

- URL: `https://stockwise-api.onrender.com/api/v1/health/live`
- Every 10 minutes, HTTP GET, expect 200

**Use `/health/live`, never `/health`.** `/health` pings the database; checking it every 10 minutes keeps Neon awake all month and uses up its 100 free compute-hours in about two and a half weeks. `/health/live` doesn't touch the database, so Neon still scales to zero when nobody uses the app and wakes in under a second on the next real request.

## 7. Smoke test

On `https://<site>.netlify.app`: register a business, log out and in, reload the page (refresh token), create a product with opening stock, and check its movement history. Then open `/api/v1/inventory/reconcile` while logged in (or check the dashboard) to confirm stock totals.

## 8. Updating

Merge into `main`. Netlify and Render both redeploy; Render applies new migrations on start. If a migration fails, the API doesn't start and the previous version keeps serving, so check the Render deploy log.

## 9. Backups

Neon's free plan keeps only a short restore window. Until you move to the VPS, take a dump weekly and before risky migrations, using a `pg_dump` whose major version is at least the Neon project's Postgres version (shown in the Neon console):

```bash
docker run --rm -v "$PWD:/out" postgres:17-alpine \
  pg_dump "<direct URL>" -Fc -f /out/stockwise-$(date +%F).dump
```

Keep the files off your laptop as well (a private cloud folder is enough for now).

## 10. When to move off the free tier

Move to the VPS plan when any of these happens: a shop uses it daily, the Neon storage or compute limits get close, or you need nightly automated backups. The only repo changes needed then are the production Docker files from 01 §15; the app code is the same.
